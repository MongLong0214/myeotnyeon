# 실제 화면 중심의 제작 운영 — v4 최종 설계

## 결론과 한계

목표는 Tōdai 레퍼런스에 가까운 **실제 움직이는 신작**이다. 관리 도구, 회귀 검사 수, 1080p 표시는 품질의 증거가 아니다. v4는 원본의 실제 셰이더/후처리를 재사용하는 경로와 신규 샷 코드를 제공하지만, 이 배포에서 신규 영상의 시각 품질은 검증되지 않았다. 성공 표시를 만들지 말고 실제 이미지를 출력해 판단한다.

비용: 추가 유료 LLM/API·에셋·음성·음악·렌더팜·외주 금지. 기존 구독의 코딩 도우미는 제작자 보조로 사용한다. 사용자에게 모델링·리깅·설치 문제 해결을 떠넘기지 않는다. 렌더를 무료로 실행한다는 것과 제작 노동이 사라진다는 것을 혼동하지 않는다.

## 제작 경로를 하나로 제한

최종 영상 = **실제 Three.js 장면 → upstream anime renderer → PNG → FFmpeg**.

Blender가 필요하면 자산을 만드는 데만 쓴다. 같은 샷을 Blender와 Three.js 두 버전으로 제작하지 않는다. SVG/보드/실사 자료를 쓰는 경우는 이야기나 편집에 실제로 필요한 경우에 한정하며, 3D가 어려워서 핵심 행동을 정적인 도식으로 대체하지 않는다.

원본 전체 영화는 `vendor/todai`의 벤치마크다. 캐릭터·스토리를 우리 작품처럼 재명명하지 않는다. 신규 콘텐츠는 `episodes/`와 `web/world.mjs` 등에 별도로 둔다.

## 0. 먼저 한 번 하는 일: 레퍼런스를 실행해 보기

고정 커밋의 원본 장면을 네이티브 16:9로 재현한다. 제작자 제공 이미지와 원작 프레임의 얼굴, 배경 질감, 조명, 광선, 외곽선을 대조한다. 다른 장면끼리 픽셀 유사도 점수를 계산해 품질을 보증하지 않는다.

원본이 잘 나오지 않으면 브라우저/WebGL·색 변환·셰이더·라이브러리 경로 문제부터 해결한다. 원본 단계가 실패했는데 아예 다른 렌더 엔진의 저품질 데모로 대체하지 않는다. 원본 제작자의 GPU 렌더 시간은 이 작업의 실측 속도가 아니다.

## 1. 새 디자인의 실제 움직이는 대표 샷

신규 캐릭터와 신규 세트를 넣고, 4~6초 실제 연기를 제작한다. 얼굴 클로즈업, 작은 표정 변화, 고개/몸 동작, 주요 소품과의 접촉 중 이 작품에서 어려운 요소를 포함한다.

270~540px 폭의 프리뷰도 **최종 모델, 같은 재질, 같은 주요 효과, 실제 카메라**로 만든다. 폴리곤 프록시로 원작급 룩을 컨펌받지 않는다. 반대로 이야기를 먼저 시험할 때는 프록시를 써도 되지만 파일/안내문에 STORY ONLY라고 구분한다.

판단의 기준:
- 얼굴과 실루엣이 작게 보아도 읽히는가?
- 캐릭터 명암/외곽선이 배경의 회화적 질감과 구분되는가?
- 광원에 이유가 있고 얼굴이 백색으로 날아가지 않는가?
- 눈이 먼저 보고 몸이 뒤따르는가? 행동의 준비와 멈춤이 있는가?
- 손/소품/발이 접촉하는 순간이 맞는가?
- 화면을 멈췄을 때만 예쁘고 움직이면 깨지는 것은 아닌가?

점수판은 만들지 않는다. 사용자에게 대표 영상과 1~2장 비교 이미지를 보여주고 큰 변경을 한 번에 받는다. 통과하지 못하면 자산/연기/룩을 고친다. 제작관리 기능을 더 만들지 않는다.

## 2. 매 편의 E2E 흐름

| 작업 | 제작자가 하는 일 | 작업물 | 검토를 묶는 방법 |
|---|---|---|---|
| 시나리오 | 첫 상황·인물의 목적·행동·반전/보상·짧은 영어 문장 작성 | SCRIPT.md | 기존 방향 안에서는 제작자가 결정. 소재/방향이 달라질 때만 질문 |
| 브레이크다운 | 기존 캐릭터/세트/동작으로 가능한 부분과 꼭 새로 만들 부분 구분 | episode.json의 샷과 실제 의존 파일 | 별도 관리 문서를 중복 작성하지 않음 |
| 스토리보드 | 구도·시선·동작의 주요 포즈를 실제 이미지로 표현 | panels / boards HTML | 그림이 빠르면 그림, 기존 세트가 빠르면 카메라 keyframe. 둘 다 만들지 않음 |
| 음성·애니매틱 | 실제 음성 길이 확인, 컷/정지/반응의 시간 조정 | 음성 WAV, 타임라인 | 대사 길이를 고정하기 전에 정교한 립싱크를 만들지 않음 |
| 레이아웃·블로킹 | 실제 공간에서 카메라, 인물 위치, 동선, 핵심 포즈 | 샷 코드/짧은 실제 프리뷰 | 전편 문맥에서 행동이 읽히는지 확인 |
| 연기 폴리시 | 눈·표정·몸 무게·손발 접촉·동작 전환 보정 | 실제 애니메이션 | 보고 싶은 핵심 장면에 비용 집중 |
| 룩·FX | 공통 재질/조명/후처리를 적용하고 샷별 필요 부분만 수정 | 실제 look 프리뷰 | 같은 자산과 스타일이면 매번 다시 승인받지 않음 |
| 작은 전편 | 모든 샷을 같은 fps/시간으로 조립, 소리·자막 연결 | 실제 3D review.mp4 | 질문 최대 3개, 타임코드 수정 목록을 한 번에 수집 |
| 수정 | 수정 요청을 제작자 판단으로 구현, 해당 샷만 갱신 | delta renders + 재조립 | 전체 파일은 접근 가능하게 하되 변경 구간 우선 확인 |
| 최종 출력 | 필요한 크기로 PNG를 원본부터 렌더, 믹스와 자막 완성 | final MP4, SRT, 크레딧 | 기존 리뷰 파일의 단순 확대 금지 |
| 납품 | 디코드·길이·잘림·소리를 확인하고 파일 전달 | 직접 열리는 실제 파일 | 외부 게시 승인과는 별개 |

편집 시간은 샷 순서와 프레임 수에서 파생한다. 샷 자체는 local frame으로 평가한다. 순서를 바꿨다고 같은 샷의 모든 프레임을 다시 만들지 않는다. 내레이션은 shot + localFrame을 기준으로 전편 시각을 계산하므로 앞 컷 길이가 바뀌면 위치가 따라간다. 음악/효과는 필요한 경우 전편 시간축에서 컷을 넘어간다. 예제의 발소리는 각 샷 모듈의 `soundEvents(params)`에서 나와 반응 지연과 컷 순서를 따라가며, 예전 음원이 남았으면 믹스 전에 재생성을 요청한다. 3D 프레임을 다시 만들라는 뜻은 아니다.

## 3. 재사용 단위

자산 = 디자인 + 제어 가능한 모델 + 필요한 표현 + 그 자산을 쓰는 검증된 샷이다.

상호작용 = 접근 → 접촉 → 따라가기/지지 전환 → 해제 → 정착의 타이밍과 목표 위치이다. 걷기 파일 하나를 붙이는 것으로 착석/집기/시선을 해결했다고 하지 않는다.

이번 코드가 구현한 범위는 **정해진 분절형 인물·책·보행/시선·그늘 연출**이다. 범용 humanoid skeletal rig, 임의 GLB의 skinned mesh/morph targets, 옷/머리카락 물리, 립싱크는 구현하지 않았다. 특히 원본 `toonMaterial`의 vertex shader가 임의 Blender bone rig를 그대로 지원한다고 가정하면 안 된다. 실제 skinning/morph 변형과 outline/paint pass를 함께 검증해야 한다. 지원하지 않는 리그를 조용히 단순 인형으로 바꾸지 않는다.

새 이야기는 기존 상태/포즈를 조합할 수 있지만, 첫 상황·인물 의도·정보의 전환·결말은 새로 만든다. 같은 영상을 색/목소리만 바꿔 다른 이야기라고 취급하지 않는다.

## 4. 해상도로 절약하고, 정보를 지우지 않기

| 목적 | 시작값 | 유지할 것 |
|---|---|---|
| 보드/구도 | 270×480의 필요한 패널만 | 행동과 화면 내 위치 |
| 실제 연기/룩 | 360×640 | 모델·카메라·핵심 셰이더·음성·24fps |
| 읽기 어려운 얼굴/손 | 그 샷만 540×960 | 접촉·표정의 시간 변화 |
| 가는 외곽선/질감/빛의 경계 | 필요한 최종 크기 정지 화면/짧은 구간 | 최종 샘플링 특성 |
| 최종 | 1080×1920 | 승인된 편집·연기·룩 |

이 수치는 최적값을 실측한 것이 아니라 시작 프리셋이다. 프레임 스킵으로 립싱크·반응 타이밍을 바꾸지 않는다. 캐릭터 on-twos를 사용할 때도 카메라와 FX는 최종 프레임마다 평가한다.

코드는 outline 두께와 일부 회화 필터 반경을 렌더 크기에 맞춘다. 저해상도에서 모든 후처리가 최종과 픽셀 단위로 동일해질 수는 없다. 그 차이를 확인할 대표 최종 크기 샘플은 필요한 작업이며 불필요한 거버넌스가 아니다.

## 5. 실무에서 남겨야 하는 최소 기록

`episode.json`, 실제 소스/자산, 렌더 프레임, 결과 manifest만 유지한다. 승인 서버, 역할별 서명, 매 샷 점수, 토큰 예산 대시보드, 분산 렌더는 만들지 않는다.

작업 시간은 다음만 기록하면 된다: 사람이 만든 시간 / 렌더·음성 계산 시간 / 수정 때문에 다시 한 시간. 지금 코드의 elapsedSeconds는 렌더 실행 시간이고 기획·미술·수정시간이 아니다. "한 편 몇 분" 실적으로 합치지 않는다.

## 6. 최종 결과의 정직한 이름

- STORYBOARD: 이야기/타이밍 판단용. 화면 품질 근거 아님.
- REFERENCE REPRODUCTION: 다른 제작자의 코드와 작품 재현. 우리 신작 아님.
- ACTUAL SCENE REVIEW: 새 자산·동작의 실제 저해상도 영상. 최종 품질 승인 전.
- FINAL-SIZE CANDIDATE: 최종 크기 출력. 완성도 컨펌과 기술 검사는 별개.
